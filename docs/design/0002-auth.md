# 0002. OmniCode 로그인과 재인증

| 항목 | 내용 |
|---|---|
| 상태 | 1차 구현 (v0.1) |
| 작성일 | 2026-10-08 |
| 작성 | @minBuild |
| 관련 | [0001 MCP 화면 관리](0001-mcp-management.md) 8.3·14·16.1 — 이 문서가 그 "인증 미들웨어" 전제를 채운다 |
| 전제 | OmniCode 배포 1개 = 사용자 1명. 서버 관리자(SSH·SSM 접근)가 곧 소유자다 |

---

## 1. 요약

- **패스키(WebAuthn)만 쓴다.** 비밀번호·이메일·SMS 없음. 사용자는 1명이고 아이디도 없다.
- **API가 유일한 인증 경계다.** CloudFront나 엣지 함수는 인증을 하지 않는다. `/api/*`는 API 프로세스가 세션 쿠키를 직접 검증한다 (0001 16.1).
- **세션은 `__Host-omnicode_session` 쿠키 + 서버 측 저장소.** 쿠키에는 난수 토큰만 있고, 서버는 그 해시만 저장한다. `SameSite=Lax`다 — `Strict`이면 OAuth 콜백 리다이렉트에서 쿠키가 빠진다 (0001 10.3).
- **고위험 작업은 5분 이내 재인증.** 같은 패스키로 한 번 더 서명하면 세션의 `auth_at`이 갱신된다.
- **첫 패스키는 설치 토큰으로 등록한다.** 서버가 패스키가 하나도 없을 때 1회용 토큰을 `/var/lib/omnicode/setup-token`(0600)에 쓴다. 관리자는 SSH로 읽어 `/setup` 화면에 붙여 넣는다. 모든 패스키를 잃으면 관리자가 `omnicode-server auth reset`으로 다시 시작한다.

---

## 2. 목표 / 비목표

### 목표

- **A1.** 폰·PC 어디서든 패스키 하나로 로그인한다. 같은 패스키가 iCloud·Google 비밀번호 관리자로 동기화되면 기기마다 등록할 필요가 없다.
- **A2.** 0001의 `requireSession` · `requireRecentAuth` · `sessionIdOf` 계약을 운영 수준으로 구현한다.
- **A3.** 서버 관리자 권한이 신뢰의 뿌리다. 화면에서 잠겨도 SSH로 복구할 수 있다.
- **A4.** 세션 탈취의 피해를 줄인다: 쿠키는 HttpOnly, 서버는 토큰 해시만 저장, 세션 목록에서 개별 종료, 고위험 작업은 재인증.

### 비목표

- 여러 사용자, 역할, 초대
- 비밀번호·OTP·소셜 로그인
- 엣지(CloudFront) 인증. 필요하면 WAF 속도 제한만 둔다 (7장)

## 3. 신뢰 모델

| 주체 | 신뢰 | 할 수 있는 것 |
|---|---|---|
| 서버 관리자 (EC2 SSH·SSM) | 최상위 | 설치 토큰 읽기, `auth reset`, 모든 데이터 접근 |
| 패스키를 가진 사용자 | 소유자 | 로그인, 재인증, 패스키 추가·삭제, 세션 관리 |
| 유효한 세션 쿠키를 가진 요청 | 소유자 (제한적) | 일반 작업. 고위험 작업은 재인증 필요 |
| 그 밖의 모든 요청 | 없음 | 공개 경로만 (5.4) |

세션 쿠키가 털렸을 때 공격자가 할 수 없는 것: 패스키 추가·삭제, 다른 세션 종료, Hub 토큰 재발급, 강제 삭제, (Phase 2) stdio 서버 추가. 할 수 있는 것: 0001의 일반 작업 — 이것이 세션 수명을 제한하는 이유다.

## 4. 데이터 모델

API 프로세스가 `<OMNICODE_DATA_DIR>/auth.sqlite`(기본 `/var/lib/omnicode/auth.sqlite`, `omnicode` 0600)를 연다. MCP 레지스트리와 파일을 나누는 이유는 인증이 MCP 기능보다 넓은 OmniCode 전체의 관심사이기 때문이다. 스키마 버전은 `PRAGMA user_version`으로 관리한다.

```sql
CREATE TABLE auth_meta (
  key   TEXT PRIMARY KEY,               -- 'user_handle' (WebAuthn user.id, 32바이트 base64url)
  value TEXT NOT NULL
);

CREATE TABLE auth_passkeys (
  id            TEXT PRIMARY KEY,        -- credential ID (base64url)
  public_key    BLOB NOT NULL,           -- COSE 공개키
  counter       INTEGER NOT NULL,
  transports    TEXT,                    -- JSON 배열
  device_type   TEXT NOT NULL,           -- singleDevice | multiDevice
  backed_up     INTEGER NOT NULL,
  aaguid        TEXT,
  label         TEXT NOT NULL,           -- 사용자가 붙인 이름 ("아이폰")
  created_at    TEXT NOT NULL,
  last_used_at  TEXT
);

CREATE TABLE auth_sessions (
  token_sha256  TEXT PRIMARY KEY,        -- 쿠키 토큰의 SHA-256. 토큰 원문은 저장하지 않는다
  public_id     TEXT NOT NULL UNIQUE,    -- 화면·API에서 세션을 가리키는 ID
  created_at    TEXT NOT NULL,
  last_seen_at  TEXT NOT NULL,
  expires_at    TEXT NOT NULL,           -- 절대 만료
  auth_at       TEXT NOT NULL,           -- 마지막 패스키 서명 시각 (재인증 판단)
  passkey_id    TEXT,                    -- 마지막 서명에 쓴 패스키
  user_agent    TEXT
);

CREATE TABLE auth_challenges (
  id            TEXT PRIMARY KEY,
  purpose       TEXT NOT NULL,           -- setup | login | reauth | add_passkey
  challenge     TEXT NOT NULL,
  session_id    TEXT,                    -- reauth·add_passkey 는 시작한 세션에 묶인다 (public_id)
  created_at    TEXT NOT NULL,
  expires_at    TEXT NOT NULL,           -- 5분
  used_at       TEXT
);

CREATE TABLE auth_setup_tokens (
  token_sha256  TEXT PRIMARY KEY,
  created_at    TEXT NOT NULL,
  expires_at    TEXT NOT NULL,           -- 24시간
  used_at       TEXT
);
```

## 5. 흐름

### 5.1 첫 설정 (설치 토큰)

1. API가 시작할 때 패스키가 0개면 32바이트 난수 설치 토큰을 만들어 해시를 `auth_setup_tokens`에, 원문을 `<dataDir>/setup-token`(0600, 원자적 쓰기)에 둔다. 로그에는 **경로만** 남긴다. 파일에 아직 유효한 토큰이 있으면 그대로 둔다.
2. 관리자: `sudo cat /var/lib/omnicode/setup-token` → 브라우저로 `https://<도메인>/setup`.
3. 화면: 토큰과 패스키 이름 입력 → `POST /api/auth/setup/options` (토큰 확인만, 소진하지 않음) → 브라우저 `navigator.credentials.create` → `POST /api/auth/setup/verify`.
4. 서버: 토큰을 다시 확인하고 소진, 등록 응답 검증, 패스키 저장, 세션 생성(쿠키 설정, `auth_at = now`), 토큰 파일 삭제.
5. 패스키가 이미 있으면 setup 엔드포인트는 409 `conflict`.

### 5.2 로그인

`POST /api/auth/login/options` → `{ challengeId, options }` (`allowCredentials` 비움 — 등록 시 `residentKey: 'required'`이므로 브라우저가 패스키 선택 창을 띄운다. 비어 있으니 로그인 전에 자격 ID가 노출되지 않는다) → `navigator.credentials.get` → `POST /api/auth/login/verify` → 응답의 자격 ID가 저장된 패스키인지, 서명·카운터·origin·RP ID·사용자 검증(UV) 확인 → 세션 생성.

### 5.3 재인증 (step-up)

`requireRecentAuth`가 `401 reauth_required`를 돌려주면 화면이 재인증 창을 띄운다: `POST /api/auth/reauth/options`(세션 필요, 챌린지는 이 세션에 묶임) → `navigator.credentials.get` → `POST /api/auth/reauth/verify` → 세션의 `auth_at` 갱신 → 원래 요청을 한 번 다시 보낸다.

재인증이 필요한 작업:

| 작업 | 경로 |
|---|---|
| Hub 토큰 재발급 | `POST /api/mcp/hub/tokens/rotate` |
| 강제 삭제 | `POST /api/mcp/servers/:id/delete/force` |
| 패스키 추가·삭제 | `POST /api/auth/passkeys/*`, `DELETE /api/auth/passkeys/:id` |
| 다른 세션 종료 | `DELETE /api/auth/sessions/:id` (자기 세션 제외) |
| stdio 서버 생성·수정 (Phase 2) | 0001 14.1 |

### 5.4 공개 경로 (세션 불필요)

| 경로 | 이유 |
|---|---|
| `GET /`, `/mcp*`, `/login`, `/setup`, `/settings*`, `/assets/*` | 화면 HTML·정적 파일. 비밀 없음 — 데이터는 전부 `/api/*`에 있다 |
| `GET /api/auth/status` | 화면이 로그인·설정 필요 여부를 안다 |
| `POST /api/auth/setup/*`, `POST /api/auth/login/*` | 로그인 자체 |
| `GET /.well-known/omnicode/client.json` | 0001 10.3 CIMD |
| `GET /oauth/callback` | 0001 10.3. 쿠키에 의존하지 않는다 |

### 5.5 복구

| 상황 | 방법 |
|---|---|
| 패스키 하나 분실, 다른 패스키 있음 | 다른 패스키로 로그인 → 보안 화면에서 분실한 패스키 삭제 |
| 모든 패스키 분실 | 관리자: `omnicode-server auth reset` → 모든 패스키·세션 삭제, 새 설치 토큰 → 5.1 |
| 설치 토큰 만료(24시간) | 관리자: `omnicode-server auth setup-token` 또는 서비스 재시작 |

CLI는 서비스와 같은 사용자·설정으로 실행한다:

```bash
sudo systemd-run --wait --pipe --collect -p User=omnicode -p Group=omnicode \
  -p EnvironmentFile=/etc/omnicode/omnicode.env \
  /usr/bin/node /opt/omnicode/packages/api/dist/main.js auth reset
```

## 6. 세션 규칙

| 항목 | 값 | 설정 |
|---|---|---|
| 쿠키 | `__Host-omnicode_session`, `Path=/`, `Secure`, `HttpOnly`, `SameSite=Lax` | — |
| 토큰 | 32바이트 난수 base64url. 서버는 SHA-256만 저장 | — |
| 유휴 만료 | 마지막 요청 후 7일 | `OMNICODE_SESSION_IDLE_DAYS` |
| 절대 만료 | 생성 후 30일. 로그인으로만 새로 만든다 | `OMNICODE_SESSION_MAX_DAYS` |
| 재인증 창 | 5분 | — |
| `last_seen_at` 갱신 | 1분에 한 번 이하 (쓰기 줄이기) | — |
| 챌린지 수명 | 5분, 1회용, 목적·세션에 묶임 | — |
| 설치 토큰 수명 | 24시간, 1회용 | — |

세션 조회는 요청마다 DB에서 한다. 캐시를 두지 않으므로 세션 종료와 `auth reset`이 즉시 반영된다.

## 7. 요청 위조·남용 방어

- **CSRF.** `SameSite=Lax` 쿠키 + JSON 본문만 받음(폼 전송은 415) + 상태를 바꾸는 요청(`POST·PUT·PATCH·DELETE`)의 `Origin`이 있으면 공개 URL의 origin과 같아야 하고, `Sec-Fetch-Site: cross-site`면 거부(403 `forbidden`). `Origin`이 없는 요청(브라우저가 아닌 클라이언트)은 쿠키만으로 판단한다.
- **WebAuthn origin·RP ID.** `OMNICODE_PUBLIC_URL`의 origin과 호스트 이름. session 모드는 이 값이 반드시 있어야 시작한다. Tailscale 전용 배포는 `tailscale serve`의 `https://<호스트>.<tailnet>.ts.net`을 쓴다.
- **사용자 검증.** 등록·서명 모두 `userVerification: 'required'`.
- **속도 제한.** 공개 인증 엔드포인트(`setup/*`, `login/*`)는 프로세스 전체에서 분당 30회, 실패한 검증은 10분에 20회를 넘으면 429 `rate_limited`. 운영에서는 CloudFront 앞단 AWS WAF 속도 제한 규칙을 추가로 둘 수 있다.
- **엣지 인증 없음.** CloudFront는 TLS·캐시만 담당한다. 화면 HTML·JS는 공개되어도 비밀이 없고, 모든 데이터는 `/api/*`에서 세션 검증을 거친다. 0001에서 말한 "CloudFront 로그인 벽"은 이 문서로 "API 세션 검증"으로 대체한다.

## 8. API

| 메서드 | 경로 | 세션 | 재인증 | 설명 |
|---|---|---|---|---|
| GET | `/api/auth/status` | — | — | `{ authenticated, setupRequired, recentAuthUntil, session }` |
| POST | `/api/auth/setup/options` | — | — | body `{ setupToken }` → `{ challengeId, options }` |
| POST | `/api/auth/setup/verify` | — | — | body `{ setupToken, challengeId, response, label? }` → 쿠키 설정 |
| POST | `/api/auth/login/options` | — | — | `{ challengeId, options }` |
| POST | `/api/auth/login/verify` | — | — | body `{ challengeId, response }` → 쿠키 설정 |
| POST | `/api/auth/reauth/options` | 필요 | — | `{ challengeId, options }` |
| POST | `/api/auth/reauth/verify` | 필요 | — | body `{ challengeId, response }` → `{ recentAuthUntil }` |
| POST | `/api/auth/logout` | 필요 | — | 204, 쿠키 삭제 |
| GET | `/api/auth/passkeys` | 필요 | — | 목록 |
| POST | `/api/auth/passkeys/options` | 필요 | 필요 | 추가용 등록 옵션 (`excludeCredentials` = 기존 패스키) |
| POST | `/api/auth/passkeys/verify` | 필요 | 필요 | body `{ challengeId, response, label }` |
| DELETE | `/api/auth/passkeys/:id` | 필요 | 필요 | 마지막 패스키는 409 `conflict` |
| GET | `/api/auth/sessions` | 필요 | — | 목록 (현재 세션 표시) |
| DELETE | `/api/auth/sessions/:id` | 필요 | 다른 세션이면 필요 | 자기 세션이면 로그아웃과 같다 |

오류 코드(0001 14.3에 추가): `webauthn_failed`(400), `challenge_invalid`(400), `setup_token_invalid`(403), `rate_limited`(429). 기존 `unauthenticated`, `reauth_required`, `forbidden`, `conflict`를 그대로 쓴다.

## 9. 화면

- `/setup` — 설치 토큰 입력, 패스키 이름, [패스키 등록].
- `/login` — [패스키로 로그인]. 로그인 뒤 `?next=`로 돌아간다 (같은 사이트 경로만).
- 재인증 창 — 어느 화면에서든 `reauth_required`를 받으면 뜬다. 성공하면 원래 요청을 자동으로 다시 보낸다.
- `/settings/security` — 패스키 목록(이름, 만든 날, 마지막 사용, 동기화 여부), [패스키 추가], [삭제]; 세션 목록(현재 세션 표시, 브라우저, 마지막 사용), [세션 끝내기]; [로그아웃].
- 세션이 끝나면(`unauthenticated`) 로그인 화면으로 보낸다.
